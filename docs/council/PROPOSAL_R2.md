# SakhiLine council proposal R2

Date: 2026-10-19. Exact decision set: P1–P6 below. Status: candidate for explicit council votes; human implementation gate remains closed. This is a recommendation for a synthetic contest demonstration, not a live health service. No production code is authorized by this document.

## P1 — One demonstrable workflow, explicit scope reduction

Recommend one-language, online short-recording → transcript/extracted draft → worker correction/confirmation → submission → supervisor approve/return/resubmit. Include assigned synthetic beneficiary selection and identity confirmation before history access, plus text-only correction/manual entry fallback. Hindi + English medical terms is provisional pending human selection. Target is a usable visit-documentation loop, not medical advice or emergency handling.

Use React + TypeScript and Node + TypeScript with PostgreSQL and Prisma ORM (distinct from Gnani Prisma STT). No existing packages or implementation are assumed. A single service handles REST requests and the single provider adapter. The first slice is stop-and-process, not continuously filling fields. This changes the PDF's must-ship live experience and needs human approval; if live streaming is mandatory, replan explicitly rather than call recording “live.”

Defer persistent offline audio/local draft queue, PSTN, outbound reminders, risk flags/clinical thresholds, custom VAD/barge-in, GPU Evon, Redis/BullMQ, multiple languages and a 1.2s latency guarantee. Local unsaved form state may survive transient network failures while the page remains open; page-close durability is not promised. Later offline features require separate privacy, device, eviction, retention and sync design. Human voice recordings are excluded absent explicit contest/data authorization. Synthetic-only limitation and online requirement must be visible in the demo.

Success evidence: matched synthetic manual-versus-voice tasks include correction and review time; publish sample counts and distributions. No time-saving percentage is asserted before measurement. Prototype product targets are >=90% end-to-end task completion over at least 10 scripted tasks, zero observed wrong-beneficiary submissions in that set, and complete keyboard operation; small samples are not safety proof. Accuracy and latency are reported rather than invented as release outcomes. The language, target set and protocol must be frozen before measuring.

## P2 — Verified speech contract and pinned extraction

Before application integration, implement a bounded provider/device spike after explicit credit-spend authorization. Pin a supported recorder → server validation/conversion → documented Gnani short-clip REST contract; default maximum clip 30s and application limit 10 MiB, with stricter vendor constraints taking precedence. These limits are product design values, not vendor guarantees. Validate actual MIME, decoded codec, duration, channels and size; do not trust extensions or browser declarations. If recorder produces unsupported WebM, convert under bounded CPU/time/resource limits or choose a verified format; never send it under a fake MIME type. Confirm deployment conversion tooling before selecting that option.

Gnani credentials remain server-only. No paid benchmark, automatic failover, GPU rental or vendor account change is authorized now. Fix the extraction provider/model/prompt/schema versions after an approved small fixture comparison, scoring both schema validity and correct fields. Until then use clearly marked fixture mode for planned local development, never present fixtures as live model results. Full streaming is a later contract with PCM framing, pacing, credentials proxying and segment semantics; don't infer partial-token support.

LLM proposes structured observations only and has no database/network tools or commit authority. Context includes authorized history labeled historical; missing current observations never inherit old readings. Separate transcript and data from instructions. Schema validation plus semantic checks and worker confirmation are mandatory. Ambiguous/unsupported values stay unresolved and trigger deterministic clarification templates. On timeout or exhausted credits, preserve user edits and show retry/manual entry; never manufacture results.

## P3 — Transactional, scoped, versioned visits

Core entities: Actor (issuer+subject, role, organization), Beneficiary (synthetic reference), Assignment (worker-beneficiary-supervisor scope), Visit, VisitRevision, TransitionAudit, IdempotencyRecord, EvaluationRun/EvaluationResult in a separate namespace. Real identifiers/phone numbers are excluded. Authentication provider remains a gated choice; application server verifies signed identity and derives role/assignment. Fixture actor injection is restricted to tests/local fixture mode and must be impossible in externally reachable live mode. No public role-switch endpoint counts as real authentication.

Every read/write is scoped by server-verified actor and assignment, not client role hints. Minimal roster discovery may show only assigned synthetic references; history requires explicit confirmed identity context. No name-only automatic attachment or caller-ID authentication.

State machine: draft → submitted → approved OR returned → draft → submitted. Confirmation is stored separately as `confirmedRevision`; any edit creates a new revision and clears confirmation. Draft edits only in draft/returned correction flow. Returned re-open makes a new draft revision; submitted revisions are immutable. Required identity, visit time and explicit unresolved-field acknowledgements are validated at submit. Domain-reviewed units and allowed fields are frozen before implementation; no clinical normal-range thresholds invented.

Initial observation design: blood-pressure pair with explicit mmHg units, hemoglobin with explicit g/dL unit, reported TT-dose mention as documentation only, optional explicitly confirmed follow-up date, bounded visit note. Every observation is `recorded`, `not_measured`, `unknown`, or `not_mentioned`; explicit negation must be preserved in typed fields/notes. Values require source transcript span or manual source, never fabricated confidence. No default clinical value. Domain review may narrow the initial schema before G1; semantic changes require a new revision and re-review.

Submit confirms an exact immutable revision, never future model output. Use version preconditions, one transaction for state+audit+idempotency, and an idempotency key scoped to actor/resource/operation with request hash. Same key+same body returns original response; same key+different body fails 409. Stale edits/approve/return fail 409. Approved records are read-only in MVP. Corrections after approval are deferred behind a new revision/audit design. No destructive migrations; no existing data migration needed because repository has no database.

## P4 — Safe, accessible review experience

Routes proposed: `/sign-in`, `/visits/new`, `/visits/:visitId`, `/review`, `/review/:visitId`, `/evaluation`. Each future screen has a separate route component per `CLAUDE.md`. Route count is planned, not created in this council.

UX sequence: assigned roster → confirm reference/identity → history labeled previous visits → record/stop with timer → processing → editable proposed fields → review unresolved entries → explicit confirm snapshot → submit → pending review receipt with ID/version → supervisor approve or return with reason → worker correction/reconfirmation. Confirmation and submission are distinct server-enforced actions. No history exposed before identity confirmation; no unannounced navigation or overwriting worker edits with late extraction.

No arbitrary LLM follow-up/advice text is rendered or spoken. Clarifications are approved fixed templates; read-back is deterministic from the confirmed draft and may use Timbre only after provider verification. Quote user notes as untrusted reported content, never endorse them as advice. No diagnostic, triage, dosage or treatment recommendations. Keyword filters are supplemental diagnostics, not the safety boundary. Clinical flagging remains deferred until qualified policy owners supply rules and approve them.

Provide visible transcript/text alternatives, manual correction, accessible labels, focus management, keyboard flow, screen-reader status updates, non-color-only errors, >=44px primary touch controls and adequate contrast. Language and numerical read-back need a fluent reviewer. Mic denied, network loss, silence, timeout, ambiguous beneficiary and failed submission are designed states. This is not an emergency channel; no “urgent no-data fallback” claim.

## P5 — Reproducible, honest synthetic evaluation

Begin with 30 independently reviewed synthetic base scenarios for one approved language: 20 development and 10 held out, split by base scenario before paraphrasing/noise. Proposed initial conditions: clean plus two fixed noise conditions, for 90 generated cases; run only within authorized spend cap. Dataset size is a plan, not observed results; reduce runs explicitly if budget cannot support it. Ground-truth JSON precedes speech generation; generation never grades its own answers. Include number/unit corrections, negation, historical-vs-current values, relative dates, duplicate names, silence and failure cases. Fix reference visit time/timezone for relative-date tests.

Cache generated speech; use deterministic seeds/recipes/hashes, pinned STT/TTS/model/prompt/schema versions. Score exact structured values after declared normalization, with per-field expected counts, completed accuracy, wrong-value rate, missing/abstention rate, schema failure rate and coverage. Publish per-language/condition sample counts, failure counts and latency p50/p95 from recording stop to editable draft; report TTS first audio separately. Infrastructure failures remain in end-to-end denominators and are separately classified. Do not fuzzy-match wrong numbers or hide failed clips. Free-text rubric results are separate from exact-field scores.

Evaluation uses the same transcription/extraction modules but distinct synthetic fixtures and evaluation tables; it cannot create submitted visits or approve records. Run concurrency 1 and separate evaluation from interactive demo sessions; queue prioritization is deferred. Timbre-to-Prisma robustness is labeled synthetic self-consistency/robustness, not natural-worker/clinical accuracy. No volunteer recordings or external voice corpus admitted now. No score or latency claims until runs execute. Minimal scorer self-tests must catch wrong numbers, wrong units, negation, missing fields, denominator errors and split leakage.

## P6 — Observable delivery with explicit human gates

One backend deployment and PostgreSQL are the target; hosting/OIDC vendor and costs need human choice before remote use. No Redis, scheduled reminder jobs or GPU are necessary for the proposed MVP. Capture structured request ID, operation, duration, error class, provider request ID and version metadata; do not log audio, transcripts, identifiers, notes, keys or session tokens. Short-lived bounded audio staging is deleted after processing/failure, with cleanup sweep after crash; provisional maximum staging retention is 1 hour pending human retention approval. Evaluation artifacts are intentionally synthetic and separately retained with provenance.

Planned verification includes unit/contract/integration/E2E/security/accessibility/device/migration-smoke tests. Load checks default to fixture provider, not billable stress. Tests must validate server authority, unconfirmed/stale/idempotent transitions, cross-actor denial, deletion/cleanup and provider failures. CI scripts proposed in roadmap are not currently runnable. No test suite is claimed to pass.

Human gates: G0 approve contest synthetic scope, language, two-builder availability and live-to-recording reduction; G1 approve field semantics, identity/provider/hosting selection, retention and bounded credit budget; G2 approve plan and explicitly authorize implementation; G3 accept measured synthetic release checks and separately approve spend/deployment/public posting; any pilot/real data/security-policy change requires new approval. No publication or external messaging on behalf of the user occurs without explicit permission. Internal council approval does not open G2.

Next possible task after G0/G1/G2: T01 scaffold minimal React/Node TypeScript workspace and fixture-mode visit slice, with dependency manifests, one route file per screen, scripts and one meaningful smoke test. No application scaffold in this planning run. Dates in roadmap are conditional; use ranges and dependencies before fitting calendar.
